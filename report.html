Project Report

History of the Internet in Pakistan — a reflective account of the design, build, and evaluation process behind this site, submitted alongside the working website for CM1040 Web Development, Coursework 2.

Introduction

This site tells the story of how ordinary people in Pakistan got online, and how that access has shaped — and been shaped by — infrastructure, mobile technology, government policy, and the economy, from the country's first commercial dial-up service in the early 1990s through to the mobile-first, freelance-driven internet of today. Rather than a single narrative thread, the story is deliberately split across four distinct angles (physical infrastructure, mobile adoption, censorship and platform bans, and the digital economy) so a reader can either follow the chronological timeline on the home page or dive into whichever theme interests them most.

Structurally, the site is a small "magazine" with five content pages plus a references page, all rendered from JSON data through a shared templating layer rather than as hand-written static HTML. Every page follows the same pattern: a page script fetches and validates a JSON data file, then hands the validated data to a template (compiled with Handlebars) which is injected into the page. This keeps content and presentation separated — updating an article means editing a JSON file, not touching any markup — and it means the same "fact card", "stats box", and "mini-list" components are reused consistently across every article-style page instead of being duplicated per page.

Inspiration

  1. Data journalism sites (e.g. Reuters Graphics, Dawn's interactive features): the idea of pairing a short, punchy "fact card" with a supporting stat in a sidebar — rather than long unbroken paragraphs — came from how data journalism outlets present dense factual reporting in scannable chunks.
  2. CM1040's Topic 5 (Data Sources & APIs) and Topic 6 (Templating) material: the pattern of fetching JSON, validating it, and rendering it through a template rather than writing content directly into HTML is a direct application of what the module covered on separating data from presentation.
  3. Government/NGO transparency dashboards: the stats-box and mini-list sidebar components (recent outages, ban timelines) are modelled on how organisations like the Digital Rights Foundation and Freedom House present timelines of restrictive actions — small, dated, scannable entries rather than prose.

Accessibility

  1. Skip-to-content link: every page has a visually-hidden link, revealed on keyboard focus, that lets keyboard and screen-reader users jump straight past the repeated navigation to the page's main content instead of tabbing through five nav links on every single page load.
  2. aria-current="page" on the active nav link: the active page is shown visually with a highlight colour, but that's a purely visual cue — a screen reader wouldn't announce it. Adding aria-current="page" alongside the CSS class means assistive technology announces which page the user is currently on.
  3. Semantic structural elements and meaningful alt text: content is marked up with <article> for each self-contained fact card and timeline entry, <aside> for supplementary sidebar content, and <section> for grouped reference lists — rather than generic <div>s everywhere — so a screen reader user gets a real document outline to navigate by. Every illustration also has descriptive alt text (e.g. "Submarine cable and fiber infrastructure") rather than a filename or generic label.

Usability

  1. Consistent page anatomy: every article-style page follows the exact same layout — hero image, intro, fact cards on the left, stats/mini-list on the right — so once a reader learns the pattern on one page, every other page is immediately familiar.
  2. Mobile-first collapsing layout: on narrow screens, the two-column article layout becomes a single column with the sidebar content moved above the fact cards, so the "headline" numbers and timeline aren't buried at the bottom of a long scroll on a phone.
  3. Clear loading and error states: while JSON data is being fetched, the page shows a "Loading…" message instead of a blank page, and if a fetch or validation step fails, the user sees a plain-language error rather than a broken, half-rendered page.

Learning

  1. Writing a hand-built JSON schema validator: I hadn't validated data shapes without a library before. I learned this by building jsonValidator.js from scratch — a small recursive checker that walks a schema definition and confirms required fields, types, and nested array item shapes are all correct before any data reaches the template layer, so a malformed JSON file fails loudly during development instead of silently breaking the page.
  2. Composing partial templates safely with an async render pipeline: several pages need to render a shared article template and then render a stats box or mini-list into a container that only exists once the article template has finished rendering. I learned that awaiting each renderTemplateIntoDOM call in sequence guarantees the DOM is updated before the next render call runs — I initially assumed this was a race condition risk and had to actually trace through the async execution order to confirm it wasn't.
  3. Testing rendered output, not just static markup: I learned that a standard HTML5 validator run against the raw HTML files only checks the empty page shells, since the real content is injected by JavaScript at runtime. To properly check validity I had to render each page in a headless browser environment (jsdom) with the actual JavaScript executing, capture the final DOM, and validate that — which is a much stronger and more honest test than validating the static source alone.

Evaluation I — What worked well

The data/template separation is the strongest part of this project. Every article page is driven entirely by a JSON file validated against a schema before rendering, which meant that once the template and page script were written once, adding or editing content became a pure data-entry task with no HTML to touch — and any malformed data is caught immediately with a clear console error rather than producing a broken page. The reusable partial components (fact card, stats box, mini-list, article layout) also meant visual consistency across five very differently-themed pages came for free, rather than needing to be manually maintained page by page. Finally, verifying HTML5 validity against the actual JavaScript-rendered DOM (not just the static shell) gives real confidence that the site is genuinely well-formed, not just superficially clean.

Evaluation II — What could be improved

The site currently uses original SVG illustrations rather than real photographs for its hero images. Given more time, sourcing genuine archival photographs (submarine cable landing stations, early Pakistani internet cafés, PTCL exchanges) with proper licensing and attribution would tell the story more vividly than symbolic illustrations can. The wireframe feedback gathered at Stage 2 also came from a single reviewer rather than a wider group, which is a known limitation — feedback from a more diverse set of readers, particularly people less familiar with the subject matter, would likely have surfaced navigation or clarity issues that a single knowledgeable reviewer wouldn't notice. Finally, while the site is responsive across the breakpoints it was tested at, it hasn't been tested on a wide range of real physical devices — only browser dev-tools emulation — so there may be device-specific quirks (e.g. iOS Safari viewport units) that haven't surfaced yet.

Resources

Libraries

  • Handlebars.js v4.7.9 — used for template compilation and rendering across all pages (loaded via jsDelivr CDN, pinned to a specific version rather than @latest for reproducibility). Approved for use in this coursework by the module teacher.

Original assets created for this project

  • All hero illustrations (images/*.svg) are original vector artwork created specifically for this site — nothing was copied or adapted from an external source, so no attribution is required. They're noted here for transparency about their origin.
  • The template engine wrapper (templateEngine.js), the JSON schema validator (jsonValidator.js), and all page scripts, partials, and JSON data content were written from scratch for this project.

Content sources

  • Dawn — reporting on the evolution of the internet in Pakistan and multiple 2022–2025 outage reports
  • ProPakistani — reporting on submarine cable and broadband milestones
  • Ispak — historical account of Pakistan's first commercial dial-up services
  • Wikipedia — Internet in Pakistan (fibre subscriber statistics)
  • Digital Rights Foundation Pakistan & Freedom House — reporting on internet censorship and platform restrictions
  • See the References page for the complete, page-by-page source list with full citation detail for every fact used on the site.

Tools

  • VS Code with the Live Server extension, for local development and testing
  • jsdom (Node.js), for headless-browser integration testing of the rendered DOM
  • A standalone HTML5 validator, run against both the static page shells and the fully JavaScript-rendered output
